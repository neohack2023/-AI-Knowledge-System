## `AP-R68-001` — Freshness law qualified only as code-changing

- **Observed behavior:** repository guidance said prior evidence became stale after a **code-changing** head update.
- **Why reasonable:** code changes are the most obvious trust-bearing candidate mutations.
- **Actual failure:** documentation/config-only commits also produce a different immutable candidate and can alter governing behavior.
- **Repair:** reason from exact candidate identity, not file-type intuition.
- **Guard:** any candidate mismatch requires explicit transfer proof before reusing head-bound evidence.
- **Promotion:** `PROMOTED_COMMON` → `PR-COMMON-001`.

## `AP-R68-002` — Merge-ref checkout described as exact-head evidence

- **Observed behavior:** repository guidance described pull-request verification as exact-head while one CI job used the default PR merge-ref checkout.
- **Why reasonable:** GitHub's default PR checkout is convenient and often treated as “the PR.”
- **Actual failure:** the checked bytes were not the immutable candidate head the evidence claimed to bind.
- **Repair:** pin acceptance-relevant checkout explicitly to the PR head SHA.
- **Guard:** inspect the actual checkout step and require its `with.ref` to equal the immutable head expression.
- **Promotion:** generalized identity rule is `PR-COMMON-001`; the structural regression lesson remains in PR #69 candidates.
